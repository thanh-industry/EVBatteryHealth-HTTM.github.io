Beyond the specification 2 additions

Two components in this design are not required by any FR or UC. They were added in response to design review and are recorded here so the distinction between "required" and "added" stays explicit.

AdditionWhyWhereStatus
Feature attribution FR-14 requires the result to be displayed, not explained. A specialist deciding whether to act on a Failure prediction needs to see which inputs drove it; a bare probability is not reviewable. Because the deployed estimator is linear, the explanation is exact rather than approximate, so it adds no modelling risk. Components → Feature attribution designed & specified
Measurement trend FR-16 requires previous results to be viewable, which the history table satisfies. A table shows what each inspection said; it does not show the direction a battery is moving. The schema already stores an input snapshot per classification, so the data needed is captured today and no schema change is required. Components → Measurement trend designed; needs repeat data

The trend panel is marked amber deliberately: the source dataset is cross-sectional, one row per battery, so no repeat measurements exist yet. The component and its data path are specified; a real curve appears once the same battery is classified more than once. Until then it shows its awaiting repeat inspections state.

Deliberately out of scope

Per spec section 1.3: the system is an academic prototype. It does not connect to real vehicles, retrain models automatically during operation, or perform physical maintenance actions. UC-01–05 (Data Scientist / Software Developer use cases) are documented on ML Pipeline as offline, notebook- and CLI-based workflows — this mockup does not invent UI screens for them, matching the architecture diagram in spec 5.1, where only the Streamlit web application (stage 3) is a web UI.
