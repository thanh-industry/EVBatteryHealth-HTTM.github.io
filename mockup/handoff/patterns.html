Run Classification flow UC-07

Two explicit steps, not one long form: picking the record is a different task from confirming its parameters, and collapsing them into one step is what made the 67-field form feel unmanageable in early drafts.

FR-13 (submit parameters) then FR-14 (display Failure / No Failure) — the Classify action is the single transition from Step 2 to the result; both outcomes route to the same "record a maintenance assessment" affordance (UC-08) because the spec requires an assessment regardless of result, not just on Failure.

The 12-key + 9-group pattern

The deployed model takes 67 features. Asking a specialist to type 67 values for every classification is the wrong design — most of them barely move the prediction and are better defaulted from the training set's median (numeric) or mode (categorical), then surfaced only if there is a reason to correct one.

Why not all 67 in one form?
  • 67 visible inputs is a wall of text a specialist cannot visually scan for the handful of values that actually matter for a given battery.
  • Most of the 67 rarely change between classifications of the same fleet (ambient temperature, vehicle age, driving habits); re-typing them is wasted motion.
  • The 12 key fields are exactly the features most worth double-checking — the ones with the widest real-world range and the most direct relationship to failure risk (thermal, voltage, fault history).

Table overflow behaviour

Every table sits inside a .hd-table-wrap with overflow-x: auto and a min-width on the <table> itself. Narrow the browser below the table's natural width and the wrapper scrolls horizontally — the page around it never does.

This frame is pinned to 380px to force the effect on any viewport. The min-width:680px on the table is intentional, not a bug — it is the width below which columns would start truncating illegibly; the scrollbar is the correct outcome, not something to "fix" by shrinking the table further.

The min-width: 0 rule

A flex or grid item defaults to min-width: auto, which means it refuses to shrink below its content's intrinsic width. Put a wide table or a long SVG inside a flex/grid row without overriding that, and the ITEM forces the ROW wider than the viewport — before the table's own overflow-x: auto ever gets a chance to act, because the row grew to accommodate it instead of clipping it. This has broken this exact layout twice on this project.

Form validation presentation

FR-07: "validate battery input parameters against the required feature definitions before performing classification." Three rules this mockup follows for every field, with the full catalogue of real messages on States → Validation error:

1. Inline, not only a banner

The error sits directly under its field (.hd-field-error), so a specialist scanning the form finds the problem without cross-referencing a banner at the top.

2. A summary banner still appears

A count-based banner ("2 fields need attention") sits above the form so the specialist knows there IS a problem before scrolling to find it.

3. Never colour alone

Every error state pairs the red border with an alert-triangle icon and literal message text, and sets aria-invalid + aria-describedby so assistive tech announces it too.
